## Key Prompts

### 1. Initial Architecture Planning

**Prompt:**
> "We're starting a new Android project. Instructions can be found in the instructions file. We're going to start planning. This project will be built using MVVM, modern Kotlin, Clean and Solid architecture. You should log main prompts into an md file so that I can talk about it later, along with another prep document for talking about decisions made. This will be a heavily modularized project with this structure: [module list]. Any questions before we get going?"

**Outcome:** Claude explored the existing project skeleton, identified what was pre-configured (all dependencies in `libs.versions.toml`), and produced a detailed implementation plan covering all 12 modules.

---

### 2. Architecture Correction — Database Placement

**Prompt (correction during planning):**
> "Shouldn't our database be in our data module? Also I'd like a single source of truth design."

**Outcome:** Plan revised to place Room database (entities, DAOs, `GameChangerDatabase`) entirely within `:core:data`. Repository implementations now follow SSOT: always observe Room via `Flow`, refresh from network on start, surface errors without breaking the cache stream.

---

### 3. Network/Data Separation

**Prompt (correction during planning):**
> "Again, I think we are mixing network and data objects. The network module should only contain network pieces, the data should contain the local data."

**Outcome:** Hard boundary established:
- `:core:network` contains only Retrofit interface, Moshi DTOs, OkHttp, and `NetworkModule`
- `:core:data` contains only Room entities, DAOs, database, mappers, repository implementations, and Hilt modules
- Neither module's internal types (DTOs or entities) escape their module boundary — only domain models cross the boundary

---

### 4. Implementation

**Prompt:**
> (Approved plan, proceeded to implementation)

**Outcome:** Full implementation generated in order: project config → `:core:common` → `:core:domain` → `:core:network` → `:core:data` → three feature modules → `:app` wiring → unit tests → documentation → ProGuard.

## How AI Was Used

- **Architecture design:** I proposed the module structure; I refined the data/network separation and SSOT design
- **Boilerplate generation:** Build files, manifests, DI modules, and mapper functions were generated by Claude
- **Logic implementation:** Repository SSOT pattern, ViewModel `StateFlow` setup, and Compose UI were generated with explicit architectural constraints
- **Testing:** Test cases for ViewModels and Repository generated; test structure (Turbine + Mockito) matches the pre-configured test dependencies
- **Review:** Every file was reviewed before the plan was approved; architectural corrections were made during planning, not post-hoc
